# Agent Guidelines

Katl produces KatlOS, an installable, upgradeable, systemd-native Kubernetes node OS. Keep work inside that product boundary and do not preserve compatibility for designs that have not shipped.

See the [agent workflow](dev/agents/) for assignments and hand-offs.

## Product Principles

- Optimize the supported journey for a home-lab operator on a trusted network. Routine install, configuration, bootstrap, upgrade, and management should be direct and unsurprising.
- Do not expose internal metadata, artifacts, or verification steps as operator ceremony. Calculate and carry integrity information internally. Keep stricter provenance or pinning optional for users with a different threat model.
- Default routine operations to the least disruptive safe behavior. Require confirmation only for genuinely destructive or ambiguous actions, and make errors explain what the operator should do next.
- Treat local, remote, and automation paths as one product experience. Every supported interface needs clear state, progress, and recovery guidance.
- Keep release artifacts self-contained for supported journeys. Avoid hidden prerequisites or separately distributed implementation artifacts when Katl can package, discover, or generate them.
- Katl prepares and manages Kubernetes nodes; it is not a Kubernetes distribution or a replacement for user-managed GitOps.
- Keep implementation details behind KatlOS workflows unless an expert interface specifically needs them.

## Engineering Boundaries

- Use Go for product policy, state machines, validation, planning, agents, and reusable logic that benefits from unit tests.
- Use the shared retry owner for network-dependent operations, with deadline-bounded, jittered exponential backoff for failures that are transient and safe to retry, and a convergence wait for eventually consistent state. Reviewers flag hand-rolled retry and convergence loops and new network calls that bypass the shared policy.
- Keep shell to small hooks and orchestration. Shell must not own installer policy, disk layout decisions, update policy, or other substantial state machines.
- Use mkosi as the image builder through `scripts/mkosi`; do not turn mkosi hooks into the installer engine.
- Use the libvirt-backed `scripts/vmtest-run` world for automated VM testing. Do not add competing VM runners without an explicit product need.
- Prefer native systemd primitives and configuration. Do not hide systemd behind a lossy abstraction; allow native passthrough where it is the clearest interface.
- Keep the runtime root immutable and versioned. Persistent identity and workload state belong on writable state storage; `/run` is ephemeral.
- Assume EFI-only boot unless a durable design decision expands the supported scope.
- Do not commit host-specific paths such as user home directories, `/nix/store`, `/run/current-system`, or `/etc/profiles`. Use `PATH`, repository-relative paths, containerized tooling, or explicit local overrides.
- Published images and release artifacts must not contain VM test agents, fixtures, or other test-only support code.

## Single Ownership

- Give every decision one owner. Node address roles, storage selection and identity, rendered configuration such as kubeadm, kubelet, API proxy and mount units, validation rules, and health definitions each have one implementation that every path calls. Install, live apply, bootstrap, join, upgrade, and rollback differ in their inputs, not in their rules.
- Before writing code that computes, renders, validates, or derives something, find the code that already owns it and use that, or move both behind one shared owner. A second implementation of the same responsibility needs a reason recorded in a design document; similar code with a genuinely different contract is not a duplicate.
- Bind a selected target once and carry the binding. After a disk, partition, or node address is selected, later steps use the bound identity and never resolve it again by label, kernel name, selector, or the current attempt's state. `docs/internal/storage-identity.md` defines this for storage.
- Treat a defect caused by two implementations disagreeing as a missing owner. Fix it by consolidating them, and search for other pairs that own the same responsibility before considering the fix complete.

## Testing and Release Confidence

- Test operator-visible outcomes and durable contracts, not incidental formatting, timing, generated ordering, or implementation details. Fix systemic test design when failures reveal overspecification; do not mask flakes with retries or looser assertions.
- Treat a check that fails on an unrelated change as a defect to root-cause and fix immediately, not as noise to rerun. Rerun such a check only while its root cause is understood and a fix is in progress.
- Run unit tests from the development shell with `scripts/hermetic -- go test ...`. Run `scripts/check-fast` and `scripts/vmtest-run` directly. Both invoke the wrapper for their Go tests.
- Keep each test's Git and `katlctl` configuration in its own temporary directory and keep `katldev` contexts in the world's own `KATLCTL_CONFIG`.
- Set `KATLCTL_CONFIG` to a file in the worktree whenever you invoke `katlctl`. Never use the operator's configuration.
- Create fixtures in fresh temporary directories with `t.TempDir()` or `mktemp -d`; fixtures that a nested `scripts/hermetic` job must read use `workstationtest.WorktreeTempDir`, because that sandbox masks `/tmp` (see [hermetic VM test worlds](docs/internal/hermetic-vmtest-worlds.md)). Never reuse a fixed directory that needs cleanup before the next run.
- Never use `sudo` on a development or agent host, for builds, tests, evidence or cleanup. CI runners are exempt where a workflow already needs it. When a step cannot run without root, record the capability gap and the command still required, and discard evidence that was produced with it.
- Run test gates as commands and read their results. Do not spawn agents just to run gates. Wait for the command's own completion or for an `exit=` line the command writes to its own log. Never wait by polling `pgrep -f`.
- Do not run a `katldev` image build while a `scripts/vmtest-run` gate uses the same checkout's `_build/mkosi`; a run pins the installer, runtime, install-image and Kubernetes sysext outputs, but still reads the upgrade images, Kubernetes upgrade sysexts and DRBD tools image from there, so the gate would test whatever the build leaves behind. Gate runs started with `scripts/vmtest-run --flavour` or `--affected` use their own build directories under `_build/gate` and are unaffected by `katldev` builds.
- Design install and lifecycle behavior as typed, idempotent, testable transitions. Use unit tests for policy and planning, golden tests for generated assets, and VM tests for integrated boot and lifecycle journeys.
- Implement deadlines exercised by VM tests as systemd timers with production defaults and separate expiry units. Disable the timer with a test-only drop-in and bind or start the expiry unit after the test reaches the relevant state. Observe the resulting transition through the journal, unit state, or a persisted operation record. Do not wait for the production timer to elapse. Keep at least one VM assertion, on a path without the drop-in, that the production timer arms with its production value.
- Release-critical services must participate in health semantics and be asserted directly in the relevant VM journey. A successful boot marker is not proof that operator access or management paths work.
- `scripts/hermetic -- go test ./...` is the baseline unit and golden gate. Use the relevant VM tests for boot, install, update, and kubeadm flows.
- Changes affecting VM infrastructure, fixtures, boot, installation, updates, disk layout, or kubeadm state must run, on a capable host, the `scripts/vmtest-run ... -count=1` tests that the change adds or modifies, and the tests that directly exercise the changed behaviour. Run added or modified VM tests on both standard and LTS kernels. The merge queue runs the full VM regression suite for every merge group, so do not repeat whole regression groups locally unless debugging a failure there. If no capable host is available, record the exact capability gap and the command still required.
- Take a local VM gate result only from that run's own evidence. Set `KATL_VMTEST_KEEP=always`, read the `--- PASS` lines for the named tests from that run's `test-summary.txt`, then clean up the run directory. Neither an exit status nor a shared log is evidence of which tests ran.
- Verify generated systemd units with `systemd-analyze verify` where practical. Risky boot, disk, update, security, or kubeadm changes also require focused review, which should check whether the change adds or keeps a second implementation of a responsibility that another path already owns.
- Every VM gate keeps a compact evidence record (go-test.log, test summary, run manifests, scenario results) under the printed run ID and deletes heavy artifacts (disks, VM directories, images) on success. Cite the run ID and read that run's record; keep full failed-run output only while debugging and remove it afterwards.
- Clean VM run directories and worktrees only with `scripts/vmtest-clean` and `scripts/worktree-clean` from a trusted `origin/main` checkout. Invoke each by absolute path as a standalone command from outside the target. Never remove the worktree you run from or use `git worktree remove --force`, `rm -rf`, `chmod -R`, `podman unshare`, or sudo for cleanup. Report anything the scripts cannot remove.
- A release should exercise the same artifacts and supported journeys users receive. Do not infer release readiness solely from unit tests or a successful artifact build.

## User-Journey Validation

- Define every user-facing change by its operator workflow before implementing it: the exact public commands, from the operator's starting state to the outcome, with the progress, errors and end state the operator should see. Put this workflow in the issue, and record it on the PR in a comment. A change is incomplete while any step needs an internal shortcut, a missing `katlctl` command or flag, or undocumented manual work, so implement every step of the workflow, not only the mechanism beneath it. Review checks the workflow against the change before anything else.
- Every user-facing change must pass hands-on user-journey validation in a persistent `katldev` VM through the public `katlctl` interface. Automated `vmtest` coverage, unit tests, direct inspection of internal state, and a journey run for an earlier change do not substitute for it. Documentation-only changes are exempt unless they describe behavior that cannot be confirmed from the code, tests, or an earlier recorded journey; in that case, validate the specific claim in a `katldev` VM rather than the whole journey.
- The journey does not hold the PR out of the merge queue. Run it in parallel with the queue, or against `main` after the merge. Label every PR or issue that changes an operator workflow `user-facing` when it is created. Whoever runs the journey records the commands and outcomes on the PR, then adds `journey: passed`. A journey that finds a product gap opens a fix in the same milestone, labelled `release-blocker`, and the PR gets `journey: gap` plus a link to that fix. No release candidate is cut while a merged `user-facing` PR that ships in it lacks `journey: passed`, or while an open `release-blocker` issue that came from a `journey: gap` remains. A PR ships in the candidate when its merge commit is reachable from the release branch and not from the previous release tag. List candidates with ``gh pr list --state merged --label user-facing --search 'merged:>=<previous release tag date> -label:"journey: passed"'`` and drop each PR whose merge commit fails `git merge-base --is-ancestor <merge commit> origin/release/<version>`. A journey that cannot reach its state through the public interface is a `journey: gap`, not an unlabelled PR. [#861](https://github.com/katl-dev/katl/issues/861) tracks a command for this check.
- Exercise the parts of the journey affected by the change, including representative happy paths, repeat operations or applies, online changes, next-boot or reboot behavior, and safe failure or recovery paths where applicable. Verify actual Linux, systemd, Kubernetes, and persisted-state outcomes from an operator-accessible surface without relying on internal shortcuts.
- Judge the journey as a user would: require useful progress, actionable errors, the expected end state, idempotence, and no surprising disruption. Record the exact commands and outcomes on the PR. Treat a discovered product gap as a failed journey that must be fixed and rerun before the release. If the host cannot provide the required VM capability, record the exact capability gap and outstanding journey on the PR and do not claim the user-facing change is validated.
- Inside throwaway `katldev` VMs, journey agents may do anything that serves development, including masking, stopping or killing units, injecting faults, breaking links and wiping disks, to reach the state a journey needs. Judge the outcome through the public interface as usual. This permission ends at the VM: it does not extend to the host, other guests on the same host, or anything outside the VM, and it covers only development work.
- Validate environmental and product-state assumptions with read-only evidence before lifecycle mutations. When a journey fails, preserve and diagnose the failed state before wiping or reinstalling so recreation does not hide a root defect. Use wipe only when recovery is unsupported or cannot be made safe, and verify corrected inputs and the reinstall path before destroying the evidence.

## Task and Delivery Workflow

See the [development tool index](dev/README.md) for tool usage and setup.

- Record scope and acceptance criteria in the GitHub issue. Use labels for status, milestones for release scope and deferrals, sub-issues for follow-up work, and blocked-by links for dependencies.
- Review `git status --short` before editing, staging, and committing. Preserve unrelated user changes and stage only explicit task paths.
- Finish the scoped change and run the applicable formatting, unit, generated-asset, systemd, and VM gates. Complete or request focused review when risk warrants it. Recheck status, stage only scoped files, and commit with `git commit-wrapped`.
- Deliver changes through ready-for-review pull requests. Use drafts only when explicitly requested. The PR title and description become the squash commit message. The orchestrator writes the description before enabling auto-merge and updates it after every fix round. Describe the final change and why it was made, include the root cause for defects, and use `Fixes #N` when the change closes an issue. Record gate results, reasons for skipped gates, reviews, and journey evidence in PR comments. Omit routine local-check inventories.
- Every open, ready-for-review PR must be in exactly one visible state:
  - Auto-merge is on or the PR is in the merge queue.
  - The PR body starts with `Hold: <reason>` and auto-merge stays off until the hold clears. Use `Hold: after #N (reason)` for a dependency on another PR or issue, or name the maintainer precondition. Every hold names the PR, issue or precondition that clears it. Do not use a hold to order the queue or to wait for host capacity: leave auto-merge on and let the queue order the PRs. Turning off auto-merge alone does not record a hold. Remove the `Hold:` line before enqueueing because the PR body becomes the squash commit message.
  - The PR is awaiting review, shown by a label or a requested review.
- Record holds, owed journeys, pending re-enqueues, and review waits in GitHub using `Hold:` lines, labels, issue links, or requested reviews. The local state file only points to those records.
- Enable auto-merge when opening a PR unless review or an explicit hold is required. For risky boot, disk, update, security, or trust changes, the orchestrator enables auto-merge after an independent review approves it (see the [Reviewer role](dev/agents/roles/reviewer.md)). The merge queue's VM run is the regression gate, so do not hold a PR for a local rerun of tests the queue already runs.
- Fix an existing PR branch with new commits on its current head and push normally. GitHub refuses pushes to a branch whose PR is in the merge queue. Dequeue the PR with the `dequeuePullRequest` mutation through `gh api graphql`, push, then re-enqueue it with `katl-queue enqueue PR`. Do not update a branch only to catch up with `main`: the merge queue tests every PR on top of `main` and the PRs ahead of it. When a PR conflicts, rebase it onto `main` and force-push with lease to its own branch. Never merge `main` into a PR branch.
- If GitHub secret scanning or push protection rejects a push, never bypass it or use the bypass URL. Remove the secret from the commits and report the rejection to the coordinator or operator.
- When authorized to merge, enqueue the PR with `katl-queue enqueue PR`, which refuses when the PR conflicts with `main` or with a PR queued ahead of it, then follow it with `katl-queue watch PR` until it merges or leaves the queue; it can run as a background task. If it leaves the queue, `katl-queue why PR` names the reason and the failing jobs. Do not treat opening a PR as completion.
- Commit with `git commit-wrapped`, which the development shell provides, and give both title and body. Commits are authored and committed under the operator's own identity. Titles use `area: summary`, where the summary completes “When merged, this change will …”. Branch commit messages are working notes that briefly explain the change and its reason.
- End the PR description with one `Release-Note:` trailer. Use the title when it works as the release entry, a one-line reader-facing summary when it needs different wording, or `Release-Note: skip` for a PR that is internal throughout. The summary replaces the full displayed entry, so include the area label if it belongs there. Release notes fall back to the commit subject when there is no trailer. For older squash commits with multiple trailers, the generator uses the last non-`skip` value and omits the entry if every trailer says `skip`.
- Put pending operator guidance in `docs/releases/next.md` when a release needs guidance beyond one-line change entries, such as upgrade paths, required actions, compatibility or deprecation notices, known limitations, and recovery guidance. Add it while preparing that release, after verifying the behavior and commands it describes. After the final release is published, move `next.md` to `docs/releases/<version>.md`. The release generator appends `<version>.md` when it exists, otherwise `next.md`, after the generated changes; review the resulting `RELEASE_NOTES.md` for the exact release before publishing. Link to durable operational procedures instead of duplicating them, and keep transient test evidence in local working notes.
- Do not rewrite history, reset, discard changes, publish releases, or mutate unrelated external state without explicit authority.

## Code and Documentation

- Pass addresses and prefixes as `net/netip` values (`netip.Addr`, `netip.AddrPort`, `netip.Prefix`). Parse them once where they enter the program, from configuration, flags, or API input, and lower them to strings only at the edge: rendered files, command arguments, wire formats, and human output. A value that may be a hostname uses a typed host that holds either an address or a validated DNS name, never a bare string.
- Keep names concise, readable, and locally meaningful. Name functions for their action or result, and keep test names focused on behavior; put scenario detail in table cases.
- Keep examples consistent with Katl naming and supported operator workflows.
- Put durable architecture decisions in focused design documents and stable operator procedures in operational docs. Keep transient findings, command output, and host details only in local working notes.
- Record unresolved design choices explicitly rather than presenting uncertain behavior as settled guidance.
