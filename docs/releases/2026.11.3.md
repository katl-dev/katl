## Select the system disk without a hardware identity

`install.systemDisk` now also accepts these criteria, so you can install to disks that report no by-id alias, WWN or serial, including many virtual disks:

- `byPath`
- `gptGUID`
- `name`, such as `/dev/sda`
- `model`
- `size`, such as `">= 500GB"`
- `type`

Every criterion you set must match, and together they must match exactly one whole disk. Otherwise installation stops before touching any disk and lists each candidate with its identities. Katl never falls back to the first disk, a device name, or size alone.

Keep using `byID`, `wwn` or `serial` whenever the installer reports one. The other criteria identify an attachment slot, the current partition table, the order in which disks are detected, or a class of disks, and `katlctl` warns when a node relies only on them. See [System disk](https://github.com/katl-dev/katl/blob/main/docs/reference/cluster-config.md#system-disk) for the guarantee each criterion gives.

Two existing workflows now refuse earlier:

- `katlctl config init` and `config add-node` stop on a disk without a hardware identity instead of leaving it unselectable. Name it with `--node` or `--disk`, which accept a by-path alias or kernel name.
- `katlctl install apply` checks that the target is unmounted, writable and large enough when it submits the configuration, rather than later in the installation.

The installer also rediscovers disks on each status request, so a disk attached or removed while it waits for configuration appears in `katlctl install status` without a reboot.

## Reinstall with another Katl disk attached

Every install now gives its partitions and partition table fresh random GUIDs, so reinstalling the same machine no longer reuses the previous install's identities. A `gptGUID` selector therefore matches no disk after a reinstall; select the disk again from `katlctl install status --endpoint ADDRESS`.

Installed nodes now mount, write and boot only the partitions on the disk they booted from, so a disk from an earlier install can stay attached during and after a reinstall. Sometimes the node cannot tell which disk it booted from: a cloned copy of the system disk is attached, or the firmware boots another disk's ESP. The node then stops in emergency mode before mounting `/var`, and the console names the disks involved. Power off, detach the copy, and boot again; do not wipe either disk. A failed upgrade trial that stops this way returns to the previous generation after a power cycle.

A rerun of `katlctl install apply` in the same installer boot also stays bound to the system and volume disks that an earlier attempt may have changed. If those disks no longer match, the rerun is refused and you are asked to boot the installer again.

## Data volumes stay bound to their disk

A data volume now mounts only when exactly one attached partition carries its recorded partition GUID, that partition is not on the system disk, and its filesystem is the one Katl recorded. Otherwise the node leaves every volume unmounted for that boot, and `katlctl node status` reports boot health as failed. It explains, for each volume, what it found and what to do:

- **A copy of a volume disk is attached**, for example a `dd` clone. Do not wipe either disk. Detach the copy, or give it new partition GUIDs with `sgdisk --randomize-guids`, and reboot the node.
- **The disk is missing.** Attach it and reboot.
- **You replaced the disk, or recreated its filesystem.** Update the volume's selector if needed, then run `katlctl cluster apply` with [`--rebind-volume NODE/VOLUME`](https://github.com/katl-dev/katl/blob/main/docs/reference/cluster-config.md#replace-a-bound-volume).

KatlOS 2026.11.1 could record a stale filesystem UUID when it formatted an existing partition in place. After upgrading, such a volume is reported as recreated and stays unmounted until you rebind it with `--rebind-volume`. Nodes whose volumes mount normally after the upgrade need no action.

## Rolling back to an earlier release

`katlctl node generations select` now refuses before switching when the selected generation could not mount its volumes, for example after a volume was replaced and rebound.

Generations from KatlOS 2026.11.1 and earlier mount `/efi` and `/var` by partition label, so they could mount another disk's state. Katl refuses to select such a generation while another disk carries Katl partitions. Detach every other Katl-formatted disk before rolling back to one of them. Otherwise the node can become unreachable and need console recovery, because a persistent `generations select` has no automatic fallback.

## Multihomed control planes

On a control plane whose `management.address` differs from its `kubernetes.address` without NAT, `katlctl cluster bootstrap` failed with `verify Kubernetes API proxy`. The workstation API proxy now also listens on `management.address`. Changing a control plane's distinct `management.address` now also moves that listener: `katlctl cluster apply` applies it online by restarting `katl-api-proxy`. Nodes with a single address, or behind NAT, behave as before.

## Configuration apply

- Upgrade `katlctl` along with your nodes. The first `katlctl cluster apply` after a bootstrap or join no longer reports a kubeadm configuration change, nor refuses a host-configuration edit, even with `--mode next-boot`. Unchanged configurations plan as unchanged.
- A sysctl file that assigns an existing kernel parameter for the first time now applies live, when Katl can restore the previous value. Precedence across every `sysctl.d` directory decides the effective value.
- Removing a unit file from a file set now stops the unit live, rather than failing and rolling back. A unit that overrode a vendor definition starts again under the vendor definition.
- Kernel audit records no longer print in the middle of console messages, such as the system-disk refusal above. Kernel auditing stays off unless you boot with `audit=1`.
